# Master Index Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `indexes/README.md`, a single entry point listing every topic index, every project, and an inbox count, maintained automatically by `capture` and `organize`.

**Architecture:** One new subsection in the shared reference (`skills/capture/references/note-format.md`) defines the master index's content and its "regenerate in full, never patch" rule. `capture` and `organize` each get exactly one new step that regenerates it after any of their existing steps touch `indexes/<Topic>.md`, `projects/<slug>/`, or `inbox/`. No new skill, no new stored metadata, no change to `ask`.

**Tech Stack:** Markdown-only Claude Code Agent Skills, same as the rest of the system. No scripts, no dependencies, no code to unit test.

**Spec:** [docs/superpowers/specs/2026-09-18-master-index-and-bulk-import-design.md](../specs/2026-09-18-master-index-and-bulk-import-design.md) — only its "Master index" section. The spec's `bulk-import` skill is an independent subsystem (a new skill, new trigger, new consent flow) and is deliberately left to its own plan rather than mixed into this one.

## Global Constraints

- No database, no new persistent metadata store (ADR 001) — `indexes/README.md` is a plain file, fully regenerated by scan, never incrementally patched.
- No new retrieval infrastructure or `ask` hop (ADR 002) — `ask`'s `indexes/` lookup, then grep, contract does not change; the master index is a navigation aid, not a retrieval hop.
- Tier: autonomous, no new consent question (ADR 003) — same tier as `capture`/`organize` updating an `indexes/<Topic>.md` page.
- Additive only: `capture`'s and `organize`'s existing trigger phrasing, single-item behavior, and file layout don't change — each gets exactly one new step.
- `indexes/<Topic>.md`'s own file format does not change. Each topic's one-line description for the master index is generated fresh at regeneration time (by skimming that index's listed notes), not stored as new frontmatter or a new line in the topic index — avoids adding a stored field to an existing, working format for a value only the master index needs.
- Projects have no existing title/metadata file anywhere in this repo (confirmed: no `projects/` example exists in this repo or its `eval/vault/` fixture). A project's master-index title is its slug deslugified (`client-onboarding` → `Client Onboarding`) — no new per-project file.
- Both topic and project lines are sorted alphabetically (by topic name / by slug) so regeneration output only changes when the underlying vault actually changes, not with filesystem scan order — required for "regenerated in full each time... so it can't drift" to actually hold.

Replace it with:

```markdown
Indexes aren't maintained for `projects/` or `inbox/`. There's no
note-count threshold — the index exists from the topic's first note
onward.

## Master index

`indexes/README.md` is the vault's single entry point — one page
above every `indexes/<Topic>.md`, so a person opening the vault (or an
agent orienting itself) doesn't need to already know which topic to
look for. `capture` and `organize` maintain it automatically, with no
separate request needed.

Regenerate it **in full from a fresh scan** every time it changes —
never patch it incrementally, so it can't drift from the vault's
actual contents:

- One line per `indexes/<Topic>.md`, sorted alphabetically by topic:
  `[[Topic]] — ` followed by a fresh one-line description of that
  topic, written by skimming the notes it lists. The description isn't
  stored anywhere — it's generated at regeneration time, same as the
  rest of this page.
- One line per `projects/<slug>/` folder, sorted alphabetically by
  slug: the slug deslugified into a title (e.g. `client-onboarding` →
  `Client Onboarding`).
- One line for `inbox/`: `N items awaiting triage`, where `N` is a
  count of the files directly in `inbox/` — a count only, not a
  per-item list, to keep this page short and avoid duplicating
  `inbox/`'s own contents.

Regenerate `indexes/README.md` whenever `capture` or `organize`
changes any of `indexes/<Topic>.md`, `projects/<slug>/`, or `inbox/`'s
contents — the same invocation points that already touch those three,
no new trigger.

`ask` does not read `indexes/README.md`. Its `indexes/` lookup, then
grep, contract is unchanged — the master index is a human/Obsidian
navigation aid, not a new retrieval hop.

## Linking pass
```
